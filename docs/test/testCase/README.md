## 2. 用例编号规则

```
TC-<模块码>-<三位序号>
```

| 规则 | 说明 |
|---|---|
| 模块码 | GAL / PRM / WF / SET / SEC / WIN / UI |
| 序号 | 从 001 起，按文件内顺序递增，不复用已删除编号 |
| 跨模块引用 | 只引用编号，不复制用例内容 |
| 新增 | 追加到对应文件末尾，编号顺延；若模块拆分，旧编号保留并在索引标注迁移 |

示例：`TC-GAL-012` 表示资产库第 12 条。

## 3. 优先级定义

| 优先级 | 判定标准 | 执行要求 |
|---|---|---|
| **P0** | 涉及数据丢失/损坏、密钥与更新安全、无法启动、主流程完全不可用；或所有用户必走的核心入口 | 每次发版前 100% 执行，必须全部通过；可在当前单机环境真实执行 |
| **P1** | 主流程的重要分支、常用导入导出、批量操作、主要筛选组合 | 每次发版前执行，通过率 ≥ 95%；未通过必须有已登记问题单 |
| **P2** | 边界输入、异常容错、体验细节、低频组合 | 每个迭代至少执行一次或抽查；不阻塞发版 |

> P0 用例的共同要求：前置条件必须能在当前环境（Windows 单机、Python 3.12 venv、Node、可选 ComfyUI）真实满足，不依赖第二台机器或真实第三方服务。

## 4. 单条用例字段

| 字段 | 必填 | 说明 |
|---|---|---|
| 用例编号 | 是 | `TC-模块码-序号` |
| 标题 | 是 | 一句话描述验证点，动宾结构 |
| 优先级 | 是 | P0 / P1 / P2 |
| 设计方法 | 是 | 见第 5 节，可多选 |
| 前置条件 | 是 | 环境、数据、状态；写清「已在哪个页面/已配置什么」 |
| 测试数据 | 是 | 具体值或构造方式；没有数据则写「无」 |
| 操作步骤 | 是 | 编号步骤，可被他人照着执行 |
| 预期结果 | 是 | 可观察、可判定；避免「正常」「正确」这类空话 |
| 可自动化程度 | 是 | 可自动化 / 半自动 / 仅手工 |
| 关联风险 | 是 | 风险 ID（见测试方案附录 A）或 `—` |

可自动化程度判定：

| 值 | 含义 |
|---|---|
| 可自动化 | 纯逻辑/接口/store/组件测试可稳定断言，不依赖真实窗口或系统弹窗 |
| 半自动 | 需要启动应用或浏览器，关键断言可脚本化，但存在人工确认步骤（如系统文件选择器、更新器替换） |
| 仅手工 | 依赖桌面窗口、托盘、系统菜单、视觉判断，当前无法稳定自动化 |

## 5. 设计方法

依据《七大测试用例设计方法与案例分析》，并结合本项目补充「异常与容错」：

| 代号 | 方法 | 适用场景 | 本项目示例 |
|---|---|---|---|
| EC | 等价类划分 | 输入多、无法穷举：文件名、搜索词、提示词文本、分类名 | 合法/非法文件类型、空/非空搜索 |
| BV | 边界值分析 | 有上下限：名称 100 字、提示词 10000 字、标签 10 个、窗口 800×600 | 99/100/101 字 |
| DT | 判定表 | 多条件组合且有依赖：筛选组合、拖拽合法性、删除分类 | 类型 + 含工作流 + 星级 |
| SC | 场景法/流程法 | 跨页面业务链路：扫描→筛选→批量→导出；导入→提示词入库 | 全量扫描后收藏是否保留 |
| EG | 错误推测 | 已知脆弱点、历史高发模块 | 批量收藏 toggle、停扫描、scheduler 丢字段 |
| CG | 因果图 | 判定表的辅助：输入条件与输出动作的依赖 | 无提示词 + force 参数 → 是否入库 |
| OT | 正交表/组合 | 因素多但只需覆盖主要组合：排序字段 × 方向 × 视图 | 排序 4 字段 × 2 方向 |
| ET | 异常与容错 | 损坏文件、断网、缺失依赖、非法 JSON、越界路径 | 0 字节图片、损坏 assets.json |

使用方法约定：

1. 先用 EC/BV 打底，保证输入覆盖；
2. 有业务链路时用 SC 补端到端；
3. 多条件交互用 DT/OT，避免组合爆炸；
4. 对已知脆弱点必须至少有一条 EG 用例，并在「关联风险」写风险 ID；
5. 所有失败分支用 ET 覆盖，预期结果必须写清错误提示或降级行为。

## 6. 与问题模板的对应关系

| 场景 | 记录方式 | 对应模板 |
|---|---|---|
| 用例预期与实际不符，且属于功能错误/数据错误 | 新建 Bug，`关联用例` 填该 TC 编号 | `issue/bug模板.md` |
| 用例通过，但交互、性能、可维护性有明显改进空间 | 新建优化，`关联用例` 填该 TC 编号 | `issue/优化模板.md` |
| 用例因环境/需求不清无法判定 | 不建 Bug，标「待确认」，在测试方案附录 B 登记 | `issue/README.md` 咨询类 |
| 同一问题影响多条用例 | 只建一个问题单，在「关联用例」列出全部编号 | Bug/优化模板 |
| 修复后回归 | 在问题单记录回归的 TC 编号与结果 | Bug 模板「修复验证方式」 |

约定：

- 一个用例失败通常只对应一个问题单；若根因不同，拆成多条并在问题单互链。
- 问题单编号不回写到用例编号，只在用例执行记录中引用。
- 用例本身不记录通过/失败状态，执行状态写在问题单或提交说明中，避免文档双写。

## 7. 执行记录建议格式

在提交说明或问题单中使用：

```
用例：TC-GAL-004, TC-GAL-005
环境：Windows 11 / Python 3.12.3 / Node 23.9.0 / 后端端口 5000
结果：TC-GAL-004 失败（收藏清空），TC-GAL-005 失败（标签清空）
证据：%TEMP%\cn-gallery-xxx\assets.json 前后对比、截图
问题单：BUG-001
```

## 8. 维护要求

- 新增功能必须同时新增或更新用例，不允许只改代码。
- 删除功能时用例标记「已废弃」，保留编号，不直接删行。
- 用例中的界面文案以 `zh-CN` 为准；英文界面作为 i18n 用例单独验证。
- 代码行号会漂移，用例只引用文件与行为，不把行号作为唯一依据。
