> 适用范围：`docs/test/issue/` 下 Bug、优化与待确认事项的记录规范。维护方式：字段、分级或状态流转变化时同步更新本文件与两个模板；编号由人工顺延，不复用。

# 问题记录规范（Bug / 优化）

## 1. 分类规则

| 类型 | 判定 | 典型例子 | 模板 |
|---|---|---|---|
| **Bug** | 实际结果与需求/用例预期不符；数据错误或丢失；功能不可用；安全边界被突破 | 全量扫描清空收藏；批量收藏把已收藏取消；scheduler 字段保存后丢失；停止扫描无效 | `bug模板.md` |
| **优化** | 功能结果正确，但体验、性能、可维护性、文案有明显改进空间；或缺失一个非阻塞能力 | 影院退出后侧栏不复位；视频资产不支持导出工作流；桥调用散落各处 | `优化模板.md` |
| **待确认（咨询）** | 需求不清、环境限制、无法判定是否为缺陷 | 删除非空分类应采用哪种策略；视频是否应支持工作流导出 | 不建单，登记到测试方案附录 B |

边界约定：

1. **数据丢失/密钥泄露/无法启动/更新校验失效**，一律按 Bug，且至少 S2。
2. **同一现象既像 Bug 又像优化**：先按用户可见后果判断。结果错误 → Bug；结果正确只是不顺手 → 优化。
3. **取消/中断类**：若任务最终能完成、数据一致，仅无法及时中断，可按优化跟踪；若导致无法继续操作或数据损坏，按 Bug。
4. **性能问题**：有明确基线且明显超出 → Bug；无基线但可优化 → 优化。
5. **文案错误**：错别字、语义错误 → Bug（S4）；表达可更好 → 优化（文案）。

## 2. 编号规则

| 类型 | 格式 | 示例 |
|---|---|---|
| Bug | `BUG-<三位序号>` | `BUG-001` |
| 优化 | `OPT-<三位序号>` | `OPT-001` |
| 待确认 | `QRY-<三位序号>`（仅用于跟踪，不进入缺陷统计） | `QRY-001` |

- 序号全局递增，删除后不复用。
- 跨仓库/跨分支沿用同一编号，不按分支重新编号。
- 关联问题在正文写「关联：BUG-00x / OPT-00x」，不新建重复单。

## 3. 字段说明

### 3.1 Bug 必填字段

| 字段 | 说明 |
|---|---|
| 标题 | 「模块 + 现象 + 后果」，如「资产库批量收藏会把已收藏项取消」 |
| 编号 | `BUG-xxx` |
| 严重程度 | S1–S4，见第 4 节 |
| 优先级 | P0–P3，见第 4 节 |
| 模块 | 资产库/提示词库/工作流/设置/更新/安全/窗口/UI |
| 环境与版本 | 操作系统、应用版本/提交、Python/Node、后端端口、是否打包 |
| 复现率 | 必现 / 高频（>50%）/ 偶现（<50%）/ 仅一次 |
| 前置条件 | 数据、配置、页面状态 |
| 复现步骤 | 编号步骤，别人可照着做 |
| 实际结果 | 客观描述，含错误文案/数值 |
| 期望结果 | 对应用例的预期或需求 |
| 影响范围 | 受影响用户/数据/模块，是否可绕过 |
| 证据 | 日志路径与片段、截图/录屏、`assets.json` 前后对比、接口响应 |
| 首次出现版本 | 已知最早版本；未知写「待确认」 |
| 是否回归 | 是/否/未知；是则附上一个正常版本 |
| 关联用例 | `TC-xxx-xxx`，可多个 |
| 修复验证方式 | 回归哪些用例、需要什么数据、如何确认 |

### 3.2 优化必填字段

| 字段 | 说明 |
|---|---|
| 标题 | 「模块 + 改进点」 |
| 编号 | `OPT-xxx` |
| 类型 | 体验 / 性能 / 可维护性 / 文案 |
| 现状与痛点 | 现在怎样、为什么不顺手/有风险 |
| 期望效果 | 可观察的改进结果，不写「优化一下」 |
| 涉及模块与文件 | 页面、store、bridge 方法、后端文件 |
| 影响面与风险 | 是否改数据格式/桥契约/配置；回滚方式 |
| 验收标准 | 可判定的 2–4 条 |
| 优先级依据 | 影响人数、频率、是否有替代路径 |
| 是否阻塞发版 | 是/否；是则说明原因 |
| 关联用例 | `TC-xxx-xxx` |
| 状态 | 见第 5 节 |

## 4. 严重程度与优先级

| 严重程度 | 定义 | 响应要求 |
|---|---|---|
| S1 致命 | 无法启动、数据不可恢复丢失、密钥/更新安全失效、主流程完全不可用 | 立即停止合并/发版，当天定位 |
| S2 严重 | 核心功能错误且无替代路径；数据不一致；批量操作结果错误 | 当前迭代修复，发版前必须关闭 |
| S3 一般 | 局部功能错误或有替代路径；偶现但可绕过 | 排入当前或下一迭代 |
| S4 建议 | 文案、体验细节、无正确性影响 | 择机处理 |

优先级与严重程度不强制一一对应，但：

| 情况 | 优先级下限 |
|---|---|
| S1 | P0 |
| S2 | P1 |
| 涉及安全/数据 | P0（无论 S 级） |
| 仅影响内部可维护性 | P2 |

优先级定义：

| 优先级 | 含义 |
|---|---|
| P0 | 立即处理，未修复不合并/不发版 |
| P1 | 当前迭代处理，发版前有结论 |
| P2 | 下一迭代处理，不阻塞 |
| P3 | 择机，允许长期挂起 |

## 5. 状态流转

```
新建 → 确认 → 处理中 → 待验证 → 关闭
                    ↘ 重开（回归失败/复现）
```

| 状态 | 进入条件 | 退出条件 |
|---|---|---|
| 新建 | 已按模板填写，证据齐全 | 负责人确认可复现/需求成立 |
| 确认 | 已复现、已定级、已关联用例 | 开始修改 |
| 处理中 | 有明确修复方案/实现中 | 代码完成并自测 |
| 待验证 | 已附改动说明与证据 | 回归用例通过 |
| 关闭 | 回归通过，用户验收 | 若再次出现则重开 |
| 重开 | 回归失败或同现象复现 | 回到处理中 |

规则：

- 缺证据（无复现步骤/日志/截图）不得进入「处理中」。
- 修复提交说明必须写问题编号；一个提交只解决一个问题域。
- 关闭前必须跑「关联用例 + 同模块 P0」。
- 待确认（QRY）不进入缺陷统计；确认后转为 Bug 或优化，编号新建。

## 6. 必填证据清单

| 证据 | Bug | 优化 |
|---|---|---|
| 环境与版本 | 必填 | 必填 |
| 复现步骤 | 必填 | 现状描述即可 |
| 复现率 | 必填 | 不需要 |
| 日志（文件路径 + 关键片段） | 必填（涉及后端时） | 视情况 |
| 截图/录屏 | 界面问题必填 | 建议 |
| 数据前后对比 | 数据问题必填 | 视情况 |
| 接口响应/桥返回 | 接口问题必填 | 视情况 |

日志默认位置：`<项目根>/logs/comfynexus_YYYYMMDD_HHMMSS.log`（打包环境为 exe 同级 `logs`，以实际为准）。

## 7. 与测试用例的对应

| 用例执行结果 | 动作 |
|---|---|
| 预期与实际不符 | 建 Bug，填写「关联用例」 |
| 符合预期但体验/性能不佳 | 建优化，填写「关联用例」 |
| 环境不具备/需求不明 | 记 QRY，写入测试方案附录 B |
| 同一根因影响多条用例 | 只建一个问题单，关联全部用例编号 |
