# README.md 更新规范

## 文档定位

README.md 是**面向最终用户的产品介绍文档**，目的是让用户快速了解产品功能和使用方法。

## 文档事实来源（单一来源，必须遵守）

| 文档 | 承担内容 | 禁止承担 |
|:---|:---|:---|
| `README.md`（仓库根） | **产品功能介绍的唯一来源**：功能清单、系统要求、安装步骤、用户 FAQ | 架构、代码结构、构建与测试命令 |
| `source-code/README.md` | **仅源码目录导航**：目录结构、从零跑起来、需要知道的现状 | 复制根 README 的产品章节 |
| `CLAUDE.md`（仓库根） | 技术栈与版本、关键命令、架构与约定、调试与日志、构建产物规则 | 面向终端用户的功能宣传 |
| `source-code/build_scripts/打包说明.md` | 构建/打包流程与脚本参数 | 产品功能介绍 |

**规则**：同一事实只在一处描述，其他文档用链接指过去。曾出现 `source-code/README.md` 完整复制根 README 的产品章节并各自漂移（一个写"内置 MinGit 2.53.0"、一个列 xflow 聚合平台），现按上表收敛。

## 事实性要求（新增，2026-11 文档审计后加入）

1. 文档里的**每个数字、路径、命令、版本号**，必须来自实际执行的命令或代码中的 `file:line`；不能凭印象写。
2. 无法验证的性能/体验类描述（如"首屏加载 <100ms"），要么给出测量方法，要么删除，要么明确标注"未核实"。
3. 涉及"内置/自动/支持"这类能力承诺时，先确认它在仓库或发布包里真实存在（例：Git 由首次启动的 Bootstrap 下载，仓库内的 `MinGit-2.53.0-64-bit/` 不含可执行文件）。
4. 修改文档时在文末维护元数据处更新核对时间与对照 commit（见下条对"版本信息"禁令的例外说明）。
5. 产品行为变更（新增/下线功能、默认值调整）必须同步根 README；纯重构不需要同步。

## 核心原则

1. **用户视角**：从用户角度描述功能，不涉及技术实现
2. **功能导向**：说明产品能做什么，如何使用
3. **简洁明了**：每个功能用 2-3 句话说明
4. **保持更新**：新功能开发完成后及时添加到对应章节

## 内容范围

### ✅ 应该包含的内容

1. **项目简介**
   - 产品是什么
   - 核心亮点
   - 目标用户

2. **功能特性**
   - 按功能模块分类
   - 每个功能的简要说明
   - 使用场景示例

3. **使用指南**
   - 安装方法
   - 快速开始
   - 常见问题

4. **其他信息**
   - 开源协议
   - 贡献方式
   - 联系方式

### ❌ 不应该包含的内容

1. **版本信息**
   - ❌ 更新日志
   - ❌ 版本历史
   - ❌ 修复记录
   - ❌ 发布日期
   - ✅ 例外：允许文末保留**一行维护元数据**（`Last verified: <日期>（对照 commit <sha>）`），它表示"文档核实时间"，不是产品版本/发布信息；除这一行外仍禁止出现版本号、更新日志与发布日期

2. **技术细节**
   - ❌ 技术架构
   - ❌ API 文档
   - ❌ 代码结构
   - ❌ 开发指南

3. **开发信息**
   - ❌ 构建脚本
   - ❌ 测试方法
   - ❌ 依赖管理
   - ❌ 开发环境配置

## 更新流程

### 何时更新

当满足以下条件时，需要更新 README.md：

1. **新增功能模块**（如：极客模式、进程冲突检测）
2. **新增子功能**（如：预设编辑、参数验证）
3. **新增用户可见特性**（如：快捷键支持、拖拽排序）
4. **功能状态变更**（如：开发中 → 已完成）

### 不需要更新的情况

- 问题修复（bug fix）
- 界面优化（UI 改进）
- 性能提升（性能优化）
- 技术改进（代码重构）
- 开发工具更新

**例外**：若上述改动使 README 现有描述变成错误（例如某项被写成"内置/默认开启"的能力实际不存在），则属于**文档纠错**，必须更新 README。

### 更新步骤

1. **定位章节**
   - 找到功能所属的模块章节
   - 如果是新模块，在合适位置添加新章节

2. **编写内容**
   - 使用用户能理解的语言
   - 避免技术术语
   - 每个功能 2-3 句话
   - 说明功能是什么、有什么用

3. **保持格式**
   - 遵循现有的格式和风格
   - 使用统一的标题层级
   - 保持列表格式一致

4. **检查质量**
   - 确认无技术术语
   - 确认无版本信息
   - 确认描述清晰易懂
   - 确认格式统一

## 功能描述规范

### 标题格式

以**当前根 README.md 的实际写法**为准（`### 🏠 首页`、`### 🤖 AI 助手`……**没有序号**，条目为 `- **名称** — 描述`）：

```markdown
### [图标] [功能名称]

- **[功能点]** — 一句话说明它为用户做什么
- **[功能点]** — 一句话说明
- **[功能点]** — 一句话说明
```

> 本规范早期版本给出的是 `### [序号]. [图标] [功能名称]` + `**核心功能** / **使用场景**` 小标题结构，
> 与实际 README 从不一致（`grep -n "^### " README.md` 可见全部标题无序号）。下方"更新示例"里的编号标题属于历史样例，
> 新写内容请按上面的实际格式。

### 描述要点

1. **功能名称**：简洁明了，用户能理解
2. **简要介绍**：1-2 句话说明功能用途
3. **核心功能**：列出主要功能点（3-5 个）
4. **使用场景**：说明什么时候用、解决什么问题

### 语言风格

**推荐用语**：
- ✅ "一键启动"
- ✅ "自动检测"
- ✅ "快速切换"
- ✅ "实时显示"
- ✅ "智能识别"

**避免用语**：
- ❌ "通过 API 调用"
- ❌ "使用 React 组件"
- ❌ "基于 Python 实现"
- ❌ "调用后端接口"
- ❌ "重构了代码"

## 检查清单

更新 README.md 后，确认：

- [ ] 新功能已添加到对应章节
- [ ] 使用用户语言，无技术术语
- [ ] 格式与现有内容保持一致（标题无序号，条目为 `- **名称** — 描述`）
- [ ] 没有添加版本号、日期等更新信息（文末一行 `Last verified` 除外）
- [ ] 没有添加技术实现细节
- [ ] **事实核实**：新增/保留的每个数字、路径、命令、"内置/默认/支持"承诺，都能用一条命令或 `file:line` 证明
- [ ] **默认值核实**：涉及开关类描述时核对代码默认值（例：`settings_manager.py` 的 `general.autoUpdate = False`）
- [ ] 无法验证的性能声明已删除或标注"未核实"
- [ ] 每个功能描述清晰易懂
- [ ] 列表格式统一
- [ ] 标题层级正确

## 维护建议

1. **定期审查**
   - 每次发布新版本后检查 README
   - 确保功能描述与实际一致
   - 删除已废弃的功能

2. **保持简洁**
   - 避免过度详细的描述
   - 重点突出核心功能
   - 复杂功能可链接到详细文档

3. **用户反馈**
   - 根据用户反馈调整描述
   - 补充常见使用场景
   - 优化不清晰的表述

## 与更新日志的关系

```
变更来源（git log / GitHub Releases 的 release body）
    ↓
  筛选用户可感知的功能
    ↓
同步到 README.md
    ↓
  只保留功能描述
  删除版本、日期、技术信息
```

> **注意**：本规范早期写的 `更新日志/更新日志_[版本号].md` 目录在仓库中**不存在**
> （`find . -type d -name "更新日志"` 无输出，`git ls-files` 也没有）。若确实要走"本地更新日志 → README"的流程，
> 需要先创建该目录并纳入维护；在此之前，README 的变更依据以提交历史与 Releases 描述为准。
> 应用内的"更新日志"弹窗与此无关，它抓取的是 ComfyUI 上游 Releases（`backend/src/core/release_notes_service.py:43`）。

**关键区别**：

| 维度 | 更新日志 | README.md |
|------|---------|-----------|
| 目的 | 告知用户本版本的变化 | 介绍产品的所有功能 |
| 内容 | 新增、修复、优化 | 功能列表和使用说明 |
| 时效 | 针对特定版本 | 持续更新，反映当前状态 |
| 详细度 | 列出所有变更 | 只保留核心功能 |
| 版本信息 | 包含版本号和日期 | 不包含版本/发布信息；仅允许文末一行 `Last verified` 维护元数据 |

## 常见问题

### Q: 修复了一个 bug，需要更新 README 吗？
A: 一般不需要，bug 修复只记录在更新日志中。**例外**：如果修复让 README 原有描述变为错误（能力实际不存在、默认值变了），必须同步纠错。

### Q: 优化了界面，需要更新 README 吗？
A: 不需要。界面优化只记录在更新日志中，除非是新增了用户可见的功能。

### Q: 新增了一个开发工具，需要更新 README 吗？
A: 不需要。开发工具不是用户功能，不记录在 README 中。

### Q: 功能从"开发中"变为"已完成"，如何更新？
A: 删除"（开发中）"标记，补充完整的功能描述。

### Q: 如何判断是否需要更新 README？
A: 问自己：这个变更是否让用户能做之前做不到的事？如果是，就需要更新。
